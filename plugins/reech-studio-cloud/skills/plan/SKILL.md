# Plan: from an idea (or a goal) to a production plan

Needs an onboarded brand (otherwise run `gather` first). Videos live under a campaign; a campaign can also be a series ("weekly explainers") or a one-off.

## 1. What is this video for?

Don't assume it's a brand campaign. From what the person said, work out, and ask only what's missing (one short message):
- **The job** for the viewer: teach, entertain, inform, sell or launch, tell a story, give an opinion, show behind the scenes, start a conversation… or a mix, or something new.
- **What they bring:** an open goal (find the angle for me), a topic, an idea, a model video, raw material (a recording, a talk, a demo).
- **References:** a brand with a saved style (`brand_get` → `style.styles`) plans from it: the carrier, the rules, the avoid list. "My style but…" is a change for this video, written in `script.json → styleChanges` (`[{ what, why }]`). A brand without one that points to someone else's video ("algo como el de…", "hazlo igual") is at the start of a style intake (`gather`, playbook `style-intake`): analyze that video (**Analyze a video they share** below), record their opinion part by part, and go on with what they gave. Copying one reference component by component gives a template; their opinion of it is what makes it theirs. Record references in `script.json → references`; borrow structure and technique, never footage, music or script.
- **How they want to work:** propose and let them pick, iterate together line by line, or go ahead on your own. Follow their answer over any default.

## Analyze a video they share

When someone shares a video ("analiza este video", "quiero uno como este", "hazlo igual"), work it out this way, with no checkpoint before the component list. Answer in their language. The goal is to recreate it as closely as possible, so never describe or promise a reference you haven't measured and looked at frame by frame: a few glances in a browser miss most of what makes it.

1. **Get the video**, in this order:
   - **A link:** `media_analyze` with `url` (YouTube, TikTok, LinkedIn and most public posts download). If the job fails because the post needs a sign-in (Instagram usually does):
   - **Record it in their browser** when Claude in Chrome is connected: it plays the post in their own signed-in Chrome and records it, sound included (the video's length in real time). Open the post in a new tab, then run in that tab (`javascript_tool`), replacing `<UPLOAD_PAGE>` with the `media_upload_page` link for this brand and `folder: "references"`, and `<NAME>` with a short name:
     ```js
     const v = [...document.querySelectorAll("video")].sort((a, b) => b.getBoundingClientRect().height - a.getBoundingClientRect().height).find((x) => x.getBoundingClientRect().top >= -10 && x.duration > 0);
     v.pause(); v.loop = false; v.muted = true; v.currentTime = 0;
     const mime = ["video/webm;codecs=vp9,opus", "video/webm"].find((m) => MediaRecorder.isTypeSupported(m));
     const rec = new MediaRecorder(v.captureStream(), { mimeType: mime, videoBitsPerSecond: 8e6 }), parts = [];
     rec.ondataavailable = (e) => e.data.size && parts.push(e.data);
     window.__reech = { state: "recording", duration: v.duration };
     rec.onstop = () => { const blob = new Blob(parts, { type: mime }); const w = window.open("<UPLOAD_PAGE>");
       const send = () => w.postMessage({ type: "reech-recording", name: "<NAME>.webm", blob }, "*");
       window.addEventListener("message", (e) => { if (e.data?.type === "reech-upload-ready") send(); if (e.data?.type === "reech-recording-received") window.__reech.state = "handed over"; });
       window.__reech = { state: "waiting for the upload page", size: blob.size }; };
     v.addEventListener("ended", () => rec.stop(), { once: true });
     await new Promise((r) => (v.readyState >= 2 ? r() : v.addEventListener("canplay", r, { once: true })));
     rec.start(1000); await v.play(); `recording ${Math.round(v.duration)} s`
     ```
     Wait the video's length, check `window.__reech.state`, then in the upload page's tab press the "Upload <name>" button (`find` it, then click) and wait for "Done". Then `media_analyze` with that path. The muted video still records its sound. This is the person watching a post they can see, like a screen recording; never use their account for anything else on that site.
   - **The file is already in their project folder:** upload it yourself (`gather` → Assets: `media_upload_links` + a PUT), into `references/`.
   - **Otherwise:** `media_upload_page` with `folder: "references"` and ask for the file (downloaded from the app, or a screen recording). Confirm it arrived with `media_list`.
2. **Measure:** `media_analyze` with the path and, if known, `kind`, `language` and `source`. `job_wait` until done. It returns the old contact sheet, pacing and transcript, plus `visual`: layout spans (full frame or a box, what surrounds it, whether it changes inside the shot), the list of dense sheets (a frame every 0.5 s with its time) and change strips (frames around every layout change).
3. **Look at all of it:** `media_view` on **every** dense sheet in order, then every change strip (up to 8 images per call). Most of what makes a reference (text that comes and goes, a sticker for half a second, a picture that slides, a collage building up) only shows there. Never describe a frame you haven't seen.
4. **List every component** in `brands/<slug>/references/<id>/components.json` (`file_get` the draft, complete it, `file_put`): one entry per layout, text style (font feel, size, color, case, position, how it enters, how lines build up), graphic, sticker, image or clip slot, transition (cut, slide, scale), camera move, sound (music, effects) and anything else, each with its times and `match`: the library piece and the config that recreates it (`library_search`, the format's config type, the text looks in the make skill), or `"gap"` with what's missing. Keep the draft's measured entries and correct them where the frames disagree.
5. **Read the context:** the job for the viewer, audience, offer and claims, the hook (catalog ids from `library_search` with `type: hook`), the structure with times, tone, voice, music role, CTA.
6. **Write it down, always, even for a recut of the brand's own video:** `breakdown.md` (under 200 words: one-line summary, structure with times, the design, what to borrow) next to `components.json`. It stays in this brand's folders; it never goes in the shared library.
7. **Attach the person's verdict to each component** (`keep`, `avoid`, `why`, in their words) in `components.json`: the opinion is the input of a style; the measurement only describes. Then **ask for what the components need, and show the list before any script.** Many components need material the person has and we don't: photos or clips for a grid or collage around them, a pattern or image behind a box, stickers, a logo, a drawing. Always in this order: (1) **ask for theirs** first, saying what each piece shows in the reference (upload page, `folder` named after the video); (2) only if they have none, **stock** when the organization has it (`me` → flags), chosen to fit the brand and the moment; (3) only then **typographic cards** as placeholders (`cards` in the make skill: the key word of that moment as a designed tile in the brand's colors), named as placeholders in the component list so they can be swapped for real images later. Never hand-drawn shapes written as code, and never quietly drop a component for lack of material. Then show the list: what will match exactly, what will be close and how, and every gap with why. A gap is never the end of the road: the make skill says how to build a missing piece for this brand. Don't approve a script against a reference until the person has seen this list.
8. **Plan the new video** from their new context and assets with the normal flow below, recording the reference id in `script.json → references`. In make, check the stills against the reference's dense frames at the same moments, component by component, before the render.

Their own brand's video may be reused as footage if they say so (list it in `assets/index.json`). Someone else's video is inspiration only: its structure and techniques, never its footage, music or script.

## 2. Pick the playbook (or make one)

A playbook is the library's guide for one kind of video: what good looks like, what to work out before writing, where the person's input matters, the usual structure, and the self-check. `library_search` with `type: playbook`, then `file_get` the matching `library/playbooks/<id>/guide.md`.
- **One fits:** follow it. A mix (a funny explainer) → follow the main one and borrow from the other.
- **None fits:** don't force the closest one. Draft a playbook for this kind of video with the person in a few lines: the job and what makes it good, who the viewer is and what they bring, what to work out before writing, where the person's input matters, a usual structure, a self-check. Use it for this video. Saving it to the shared library is a Reech-side step: hand the draft to the team (paste it in the answer) so they add it for everyone.
- **Improve as you go:** when a person's corrections are about one brand's taste, put them in that brand's `system/writing.md` (`file_put`). When they would improve the playbook for everyone, tell the team.

The brand's `system/writing.md` (if it exists) wins over the playbook. Read it before writing.

## 3. Checkpoints

**In "just do it" mode** (the person said to go ahead on their own, or `autonomy` is `"auto"`; see `studio`), there are no stops: decide each of these yourself, write your choices and assumptions into `script.json → assumptions`, and go straight to `make`.

**Otherwise, at most three stops before the finished video**, unless the person asked to work differently in step 1. Every stop costs them a wait and a reply, so fold everything you need into these:
1. **What to make:** the brand (only if it isn't clear) and what they have in mind, in one question. If they ask for ideas, the ideas come in your next reply.
2. **Which idea:** only when you proposed ideas. Give each one its premise line, so the pick is already the angle.
3. **The script:** the one review before money is spent. Show the script together with whatever the playbook asks the person to check before writing (the viewer's doubts, the angle, the comparison: put them next to the lines that answer them, not in a separate round), the facts and their sources, what is invented to illustrate, and the production choices still open (voice, music, length) with your recommendation for each. Ask once: "Does it work, or what should change?" Their answer approves the script and the choices you recommended.
   **They can also read and approve it in their dashboard:** as soon as the script is saved, give them the video's link (`me` → `dashboardVideo`, with the brand, campaign and video filled in): it shows the script line by line (what's said, what's on screen, about when), the voice, music, versions, length and sources. There they tap a line to change what's said or shown, take it out, or comment, and press "Approve the script". Both land in the video's `rounds.json`, in the round with `stage: "script"` (round 0, kept apart from the preview rounds): its feedback items carry `ask` with `kind: "script"`, `target.path` (the place in `script.json`, e.g. `beats.3.vo`), and `value` (the exact new text), `remove: true`, or `want` (a comment, yours to resolve). When they say they're done (or paste "Aplica los cambios…"), `video_get` → `rounds`: apply each open item to `script.json` (`video_save`), set it `status: "done"` with `change`, and show the changed lines. `approved: true` on that round is their approval: go to `make` without asking again. When they approve in the chat instead, record it there too (the approve command does).


The playbook's checkpoints that come before the script are answered inside stop 3; don't hold a separate round for them. The look is decided in `make` (derived from the footage, the brand, the pace and the reference, with reasons): when the person works with choices, `make` shows two or three looks as stills of the same moments and they pick once; in "just do it" mode `make` picks and records why. After stop 3 there are no more questions until delivery: don't ask to approve the cut, the stills or the render (`make` judges those), and only ask again when something truly needs the person (a file only they have, or a choice the brand system doesn't settle and you can't decide). When a step is a choice among options and `system.json → autonomy` is `"auto"`, make the choice yourself and say why in one line. `/reech-studio-cloud:approve` records the person's approval of a script.

## 4. Production plan (every kind of video)

**Before writing it, test the premise:** say the video in one line, without the visuals. If that line isn't interesting on its own, change the idea: great footage can't save a boring premise, but a good premise survives simple footage. Also write in one line which part of the brand's positioning this video builds (`script.json → builds`).

Save the script with `video_save` (`brand`, `campaign`, `video` folder name in lowercase-with-dashes, `script`): `profile` (`studio/brands/<slug>/system/profile.json`), `playbook`, `concept`, `format`, `objective`, `engagement`, `hook_type`, `beats[] {id, vo, card/shot notes}`, `facts_checked {claim: source}`, `footage[]` (paths under `brands/<slug>/` or `library/`, relative to `media/`), plus whatever the playbook adds. Look at an existing video's `script.json` (`video_get`) for the shape. Then:

- **Voice-led or picture-led?** Decide first.
  - **Voice-led** (explainers, listicles, a brand's series): the voice is the spine; on-screen text and footage illustrate the line being spoken. Write for the ear: short sentences, the local language and dialect, the brand's voice direction.
  - **Picture-led** (commercials, brand films, stories, anything shot or generated as scenes): write the film first, shot by shot, as if it had no voice. Then add only the few lines that say what the picture can't: about 1.5 words a second at most, planned silences (`script.json → max_voiceless_gap_s`, with the reason), and no line that describes what's on screen.
  - Length from the playbook, the platform plan or the model video; otherwise 20–40 s.
- **The voice is chosen for this piece.** With ElevenLabs enabled, the brand's profile voice only when the playbook or the person says it fits; otherwise `script.json → voice {voice_id, name, why}` overrides the profile. Take the `voice_id` from `voices_list`; a voice that isn't on the account fails. Without ElevenLabs, the plan names who records it and how (`script.json → voice_source: "recording"`), and the recording is transcribed in `make`.
- **Hook** in the first second, in both the words and the picture. Pick it from the hook catalog (`library_search` with `type: hook`: each entry has the feeling, the question, how to make it, whether it works muted, and example references); combine two when it helps. Testing rules (rulebook `research-testing`; follow them by default, break them on purpose when the idea needs it, and say so): the hook makes the viewer feel something and leaves a question (RT-05); it opens broad and narrows in the middle and CTA (RT-06); the brand is recognizable within 2 s, in the scene, spoken or by sound, not a bare logo (RT-01, `script.json → brand_cues [{t, asset, kind}]`). **CTA** that asks for the action the video is after.
- **Feeling and showmanship** (RT-02/03/04): name the feeling the video builds (`script.json → feeling`); count people, place, story, dialogue and melody against voice-over monologue, wall-to-wall text, fast montage and abstract product shots (`showmanship {right, left}`); let the first on-screen text frame how to watch rather than cover the video. The brand's recurring device, if it has one, goes in `brand_device` (RT-07).
- **One test when it's cheap.** If a testing rule is in question for this brand and the video can carry two variants, plan one: `script.json → test {rule, a, b}`. Learn compares them. Don't test more than one thing per video.
- **Rotation:** check `posts_list` and `history.json` so the same device, hook or phrase isn't repeated too soon.
- **Shots:** what each beat needs, marking what already exists (`media_list` for the brand; `library_search` with `type: media` for shared stock) and what must be sourced, uploaded or generated.
- **Format × style:** the format that fits (`library_search` with `type: format`, read its manifest and config type with `file_get`), and a look that fits the piece. A brand's series style belongs to that series. For other pieces take the brand's essentials and let the piece's own look lead; the brand serves the piece, it doesn't cover it. If it needs something the library doesn't have, say so: new formats, styles and components are a Reech-side step (ask the team); `make` works with what the library offers.
- **Deliverables per platform** (`library_search` with `type: platform`): aspect ratios, lengths and cutdowns, cover frame, caption file, A/B hook variants if a test is worth running.

- **Walk it in 3-second blocks, as the viewer.** Before anything is produced, go through the script and shots three seconds at a time as someone who doesn't care yet: what do I see and hear, do I care, and what makes me want the next three seconds? Rewrite any block that fails. Write the walk in `script.json → viewer_walk` (`[{t: "0-3", sees, hears, why_stay}]`), and show it with the script when the playbook has a script checkpoint. Write the hook in `script.json → hook {ids, emotion, question}`.

Fact-check every claim before any money is spent on audio. Then hand over to `make`.
